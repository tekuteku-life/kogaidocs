## 1. 開発プロセスの目的と基本原則

本開発プロセス定義書は、機微な児童・役員個人情報を取り扱う「完全ローカル・プライバシーファースト型」システムとしての高いセキュリティ・堅牢性・保守性を維持しつつ、ユーザー要求に迅速かつ安全に応えるための標準開発手順を定めるものである。

### 基本原則
1. **Holistic & Objective-Driven Design（全体最適・あるべき姿の追求）**
	- 要求に対する場当たり的・局所的な継ぎ接ぎ修正を厳禁とし、システム全体のアーキテクチャ・データフロー・ユーザー体験（UX）を見渡した全体最適設計を行う。
2. **Defense-in-Depth Security First（多層防御の徹底）**
	- どんな機能改修であっても、ゼロトラスト・暗号化原則（AES-256-GCM, WebAuthn, メモリ限定鍵管理, 入力サニタイズ）を緩めてはならない。
3. **Multi-Stage Subagent Quality Gates & Code Reviews（多段階レビューゲートと実装コードレビュー）**
	- 設計フェーズ（Gate 1）、テストフェーズ（Gate 2）、実装後コードレビュー・総合監査フェーズ（Gate 3）の各段階において、独立したサブエージェントによる厳格なレビューゲートを通過することを必須とする。
4. **Mechanical Syntax Verification & Static Type Review（機械的構文チェックの義務化と静的型・参照の整合性の確認）**
	- 人手の目視確認に依存せず、機械的に構文チェック（`node -c`）および機械的に静的型・DOM整合性・スキーマチェックを実施し、文法・型・参照上の欠陥を完全にゼロとする。
	- 各ゲートへ出す前に、`tests/scripts/` の機械的チェック（4.6）を実行する。機械で見つけられる誤りを、ゲートの指摘で見つけさせない。
	- 例外: 静的型・参照の整合性（Stage 7 の 2.。存在しないプロパティ・必須プロパティの欠落・ID 体系・ドメイン値・DOM の ID）は、機械的に網羅できないため、試験（単体・実Chromium）と Gate 3 の重点検査項目（4.4）で確かめる。
5. **Tri-Tier Test Coverage: Normal, Boundary & Abnormal（正常系・境界値・異常系の全方位テスト実装義務）**
	- テストスイート（単体・結合・システム・ヘッドレスChrome UIテスト）においては、正常系（Happy Path）にとどまらず、境界値（Boundary Values）および異常系（Abnormal / Error / Injection / Validation Failure）のすべてを網羅して実装することを義務付ける。
6. **Headless Chrome Real-UI Testing（ヘッドレスChromeによるUI実体テストの必須化）**
	- モック環境のみの検証を排し、ヘッドレスChrome（Chromium）実ブラウザ環境下で、実DOM構造、CSSレイアウト、イベント発火、モーダル開閉、印刷プレビュー、Web Cryptography API連携を自動検証するUIテストをライフサイクルに組み込む。
7. **Zero Dead Code & High Test Coverage（不要コードの完全排除と高網羅率）**
	- 機能追加・改修によって生じた不要コードや旧互換コードを即時削除し、命令網羅（Line）100%、分岐網羅（Branch）95%以上を全モジュールで維持する。
8. **Commit & Remote Push Completion（コミット＆リモートpush完遂原則）**
	- すべてのプロセス完了時の作業完了定義（Definition of Done: DoD）はローカルコミットにとどまらず、必ずリモートリポジトリへのプッシュ（`git push`）までを完了要件とする。
9. **Branch & Pull Request-Driven Development（ブランチ・プルリク駆動開発の徹底）**
	- `main` ブランチへの直接コミットを原則禁止とし、必ず作業用ブランチ（`feature/*`, `fix/*`, `docs/*` 等）を切って作業を行い、所定のプルリクフォーマットに基づくPR発行・レビューを経てマージする（※ユーザー指示により直接main作業が承認された軽微なドキュメント修正等を除く）。
10. **Strict Rework & Retest Loop（手戻り発生時の全先行検証・レビュー再実行原則）**
	- 開発プロセスの途中でレビュー指摘（Gate 1〜3）やユーザー指摘による手戻りが発生した場合、局所的なパッチ修正を禁止する。修正内容が影響を及ぼす先行ステージ（設計改訂、設計レビュー、テスト実装、テスト網羅性レビュー等）まで必ず立ち戻り、先行する検証およびレビュー手続きを漏れなく再実行すること。ただし、指摘が文書の表現・記述の精度だけに関するもの（4.1 の 4.）は、ゲートを通過として並行して直す。将来のコードの潜在の経路だけの指摘（4.1 の 5.）は、検査に加えて反映し、再審査なしで通過とする。今回の変更で生じたものではない変更外の指摘（4.1 の 6.）は、残件台帳に記録して通過とする（配信側の事項は 4.7 のとおり台帳に載せず、設計書に範囲外・前提として書く）。
11. **Root-Cause Analysis, Horizontal Scan & Test-Driven Hardening（完了後不具合の横展開調査とテスト先行強化原則）**
	- プロセス完了後（または運用後）にユーザー指摘等で修正・不具合が発生した場合は、単一箇所の修正で終わらせず、システム全体における類似不具合・類似パターンの有無を網羅的に横展開調査すること。さらに、当該不具合および潜在的類似不具合を確実に検知できるようテストスイート（単体・結合・システム・UI実体テスト）を先行して拡充・修正し、テスト側の網羅性確認およびレビューを完了させてから本線修正・マージを行うこと。

## 3. 各ステージの実施要領

### Stage 0: フィーチャーブランチの作成と命名規約
- `main` ブランチを最新状態に更新後、作業内容に応じたプレフィックスを付与したブランチを作成する。
- **ブランチ命名規約**:
	- `feature/<feature-name>`: 新機能開発、機能拡張
	- `fix/<bug-name>`: バグ修正、不具合対応
	- `docs/<doc-name>`: 設計書・ドキュメント・テンプレートの改訂
	- `refactor/<refactor-name>`: リファクタリング、コード整理
	- `test/<test-name>`: テストケースの追加・強化
- 例: `git checkout -b feature/headless-ui-tests`
- ※例外措置: ユーザーからの明示的な指示があり、ドキュメントの改訂や軽微な修正等である場合は、直接 `main` ブランチでの作業が認められる（ただし構文チェック・レビュー・push手順は省略不可）。

### Stage 1: 要求分析と全体最適化構想
- ユーザー要求の背景・意図（ユーザーが真に解決したい課題）を深く分析する。
- 局所的な対処（例：ただフラグを立てる、単なるボタン増設）を避け、UI階層、状態管理、暗号化基盤の観点から「システムのあるべき姿」を描く。
- セキュリティ影響度（新機能が暗号化や個人情報保護に及ぼすリスク）を事前評価する。
- 残件台帳（`docs/review_backlog.md`）の未対応の項目のうち、今回の変更の範囲に関わるものを確かめ、今回対応するか見送るかを決めて状態を更新する（4.7）。
- 比較元（今回の作業の着手前のコミット）を決め、記録に書く。以後の `--base` にはこれを使う。

### Stage 2: 要件・外部仕様・内部仕様の改訂
- 実装を開始する前に、`docs/requirements.md`、`docs/external_design.md`、`docs/internal_design.md` を最新化し、`docs/specification_traceability.md` に要件・仕様・実装・実アサーションと未検証境界を対応づける。`docs/system_design.md` は案内と旧章の移行先だけを保持する。
- 更新対象セクション：アーキテクチャ図、データモデル、シーケンス、UI/UX仕様、セキュリティ仕様、不要コード削除方針。
- 設計書のバージョンをインクリメントし、タブインデント規約（`\t`）を徹底する。
- **影響範囲の一覧（必須）**: 変更するデータ・規則・関数ごとに、それを読み書きする経路を全部挙げ、経路ごとに「変える／変えない」を決める。`node tests/scripts/impact.js --callers 3 <名前>...` で、出現（それを含む関数つき）と呼出元をたどった経路、書き換えの候補になる既存の試験の一覧を作り、漏れがないことを確かめる。
	- 一覧は設計書（内部仕様または追跡表）に表として置く。経路ごとに、旧版との差（同じ／意図して変える）を書く。
	- 理由: SPEC-Q では、出席の変更が座席の引継ぎに及ぶことを設計で挙げておらず、終盤（Gate 1 の差分22回目）に退行として見つかり、設計まで戻った。
- **検査の目的と対象外**: 字句の固定のような網羅しきれない検査を設けるときは、その検査が何を検出するためのものか、何を対象外とするか（難読化・別の防御で止まる経路など）を設計書に書き、ゲートの依頼文にも示す。
- ゲートへ出す前に `node tests/scripts/check-docs.js --base <比較元> --pending <この回の記録>` を実行し、問題が0件であることを確かめる（結果待ちのプレースホルダーは、その回の記録の中だけ許す）。比較元にもある問題は「変更外」として分けて出るので、残件台帳にない項目を台帳に記録する（4.7）。

### Stage 3: 設計レビュー＆セキュリティアセスメント（第1ゲート）
- 独立サブエージェント（QA & Security Lead）を召喚し、改訂された設計書を精査する。
- **レビュー観点**:
	1. ソフトウェア工学観点: 凝集度、結合度、拡張性、既存機能との整合性。
	2. セキュリティ観点: 脅威モデリング（STRIDE）、暗号鍵管理、認証バイパスの有無、XSS/データ漏洩耐性。
	3. **不足観点精査**: 不足する設計や考慮漏れ、エッジケースの未定義がないかの徹底チェック。
	4. **Mermaid構文チェック**: レビュー報告書内に Mermaid 図を含む場合は構文エラーチェックを必ず実施。
	5. **影響範囲の一覧の漏れ**: 1回目は、Stage 2 の影響範囲の一覧に挙がっていない経路がないかを主な観点とする。
- レビュー結果を評価レポートとして `docs/reviews/reviewX_design.md` に保存する。

### Stage 4: テスト設計と全方位テストスイート実装（TDD/テストファースト）
- **手順の順序**: (1) 着手前の不安定な試験の一掃 → (2) 試験の実装 → (3) 実装がない状態での確認 → (4) 実装の下書き（Stage 6 の先行） → (5) 下書きへの変異の当て込み → Gate 2。Gate 2 の審査対象は試験で、下書きは変異の当て込みの対象として示す（下書きは Gate 3 で審査する）。
	- (3) の確かめ方は、影響範囲の一覧（Stage 2）の経路の区分で分ける。
		- 「変える」経路の試験: 実装がない状態で失敗することを確かめる。
		- 「変えない」経路の試験（退行の試験。座席の引継ぎなど）: 比較元でも合格することを確かめる。
- **着手前の不安定な試験の一掃**: 次の試験を `node tests/scripts/repeat-tests.js --times 10 --coverage --load 2 <試験ファイル>...`（実Chromium の試験は `--times 3`）で繰り返し実行する。対象は、影響範囲の一覧の名前を含む試験と、実Chromium・時刻・待機に依存するすべての試験（`tests/system/headless-*.test.js`、自動ロック・タイマーの試験）とする。
	- 所要時間は、試験ごとに、その試験自身の上限の半分と比べる。上限は runner の `timeoutMs`（既定 20000ms）と node:test の `timeout` で、上限の表 `tests/scripts/stress/test-limits.json` に書く（試験名つきの規則、ファイルの規則、`*` を含む規則の順に優先する）。
	- 試験の上限を変えたとき・上限のある試験を足したときは、上限の表も直す。時間切れそのものを確かめる試験（runner の `timeoutMs: 1500` の試験など）は、表の `exempt` に理由を書いて比較から外す。
	- 表に漏れがないことは `tests/unit/dev-scripts-repeat-tests.test.js` で確かめる（すべての試験ファイル（開発用のスクリプトの試験を含む）の、runner の `timeoutMs: <数>` と、試験・suite（`describe`・`suite`）の宣言の引数の `timeout: <数>` ごとに、その試験に当たる規則が同じ上限か `exempt` であること、runner の既定の `timeoutMs` と `headless-*` の規則が同じであること、runner を読み込む試験ファイルに規則があること。宣言の引数でない `timeout` は、`mutate.js` の `runMutants`・`runTests` の引数だけを許し、それ以外（変数で渡す options など）は問題とする）。
	- 保存の完了を遅らせても合格することを、`node tests/scripts/mutate.js --spec tests/scripts/stress/save-delay.json` で確かめる（合格を期待する変異）。
	- 落ちた試験・上限の半分を超えた試験は、本題の前に別のコミットで直す。
	- 理由: SPEC-Q・R-25 の作業では、SEC-31・SEC-34・自動ロックの判定の不安定さ（負荷をかけたときだけ出るものを含む）と、上限 30000ms に対して約20秒かかる試験が、Gate 3 や Gate 2 の終盤で見つかり、そのたびに全体をやり直した。
- **単位ごとの実行と記録**: 着手前の一掃と変異の当て込みは、単位ごとに実行する。単位は、一掃では試験ファイル1つ、変異では変異の対象のファイル1つとその試験のファイルの組とする。変異の対象のファイルは、その作業で実装として変えたファイル（本番のファイル js・sw.js。開発用のスクリプトを作る作業では `tests/scripts/` の .js も）とする。
	- 実行は `node tests/scripts/run-units.js --units <単位の一覧> --records <記録の置き場所>`（4.6）で行う。単位の一覧と記録の置き場所は作業ツリーの外に置き、作業の間は同じ記録の置き場所を使い続ける（記録を使い回すため）。写しの根を写す最上位のスクリプト（`mutate.js`）が引数のほかに読むファイルは、一覧の `inputs` に書く（その読取りは入力にしない。4.6）。`--only` なしで実行し（記録を使い回す）、終了コード 0 か 1 で終わったときの記録の置き場所の `summary.md`（結果の表）を記録に貼る（信号・例外で止めた実行の表は、止めた単位の行を欠く）。
	- 単位ごとに、結果（終了コードと出力）、実行のしかた（実行のコマンドと引数、Node.js の版、実行の仕組みの SHA-256、実行の環境、起こしたプログラム。4.6 の `run-units.js` の (7)）、入力のファイルごとの SHA-256 を記録する。
	- 入力は、その単位の実行が読むすべてのファイルとする（対象のファイル、試験のファイル、試験が動かすコード、試験が読み取り・走査するファイル、実行に使うスクリプト `repeat-tests.js`・`mutate.js`、上限の表、変異の一覧と等価の一覧）。実行の間に読んだファイルを記録して求め、記録できないもの（ブラウザーが `file://` で読むアプリのファイルなど）は、その種類のファイルをすべて入力に含める。読むファイルが分からない単位は、写しの全体を入力とする。
	- 入力の SHA-256 は、実行した写しから求める。
	- 実行は作業ツリーを固めた写しの上で行い、その間も作業ツリーでの直しを続ける。写しには審査の記録（`docs/reviews/`・`docs/review_backlog.md`）を入れない（試験はこれを読まない。写しの全体を読む単位の入力が、結果を記録に書くたびに変わらないようにする）。
	- 直した後にやり直すのは、不合格の単位と、合格した後に入力か実行のしかたが変わった単位だけとする。記録した結果を使うのは、合格していて、実行のしかたが同じで、記録した入力のファイルがすべて同じで、今の単位の定義の決まった入力（対象・試験のファイル、実行に使うスクリプト、一覧など）がすべて記録の入力に含まれるときだけとする。
	- 試験は、単位ごとに実行できるよう、対象のファイルごとに試験のファイルを分ける（`tests/unit/dev-scripts-<スクリプト>.test.js` など）。
	- 開発用のスクリプト（`tests/scripts/`）の試験は POSIX（Linux・macOS）で実行するものとする。Windows では、シンボリックリンク・シグナル・プロセスグループ・`/proc`・Windows のファイル名に使えない文字に依る試験を、試験ごと除く（試験を部分に分けない）。理由: `run-units.js` の作業の Gate 2 で、Windows での除き方の指摘（除き漏れ・除きすぎ）が3回続いた。開発用のスクリプト自体がシンボリックリンク（写しの `node_modules`）・プロセスグループ・`/proc` を使い、ほかの開発用のスクリプトの試験も Windows を個別に扱っていない（利用者の決定。[review100](reviews/review100_unit_runner_tests.md)）。
	- 理由: 開発プロセス v1.8.0 の作業では、一掃と変異を全部1本で順に実行していたため、実行の間は作業ツリーを変えられず、1つの単位が失敗しても全部をやり直していた。
- 単体テスト（`tests/unit/`）、結合テスト（`tests/integration/`）、システムテスト（`tests/system/`）、およびヘッドレスChrome UIテスト（`tests/system/headless-chrome.test.js`）を実装する。
- **試験の仕組みは単純な方式から**: 試験の補助（範囲の判定、runner の拡張など）を新しく入れるときは、環境に依存しない最も単純な方式を先に試す。Git・環境変数・利用者の設定に依存する方式は、必要な理由を書いた場合だけ使う（R-25 では Git に依存する一覧が副作用を生み、元に戻した）。
- **変異の当て込み（Gate 2 の前に必須）**: 実装者は、実装の下書きに規則ごとの変異（条件を外す・比較を反転する・分岐を削る・件数を変える）を `node tests/scripts/mutate.js` で当て、生存がないことを確かめる。一覧で書く変異と、`--auto` の演算子変異（下書きの変更した行の範囲）の両方を使う。`--auto` は比較・論理演算・否定・真偽値だけを変えるので、条件や分岐・呼出しを外す、件数・定数・既定値・正規表現を変える変異は、規則ごとに一覧（`--spec`）で書く。変異の一覧と結果の表を Gate 2 の依頼文に付ける。
	- 生き残った変異は、試験を足すか、意味の変わらない変異であることを書く。一覧の変異は項目の `equivalent` に、`--auto` の変異は `--equivalents` の一覧（表の「変異」の列の名前 `<行>:<列> <演算子>` と理由）に書く。
	- Gate 2 に出す時点の、比較元から変えたすべての変異の対象のファイル（上の「単位ごとの実行と記録」。本番のファイル js・sw.js と、開発用のスクリプトを作る作業では `tests/scripts/` の .js）の写しを、作業ツリーの外に保存する（Stage 7 の当て直しの `--since` に使う）。
	- 理由: SPEC-Q の Gate 2 では、レビュワーが変異を1つずつ見つける回が約30回続いた。置換の誤りで変異が入らないまま合格と判断した例もあった（`mutate.js` は置換が成立しない変異・構文が壊れる変異を「無効」として報告する）。

## 4. 手戻り管理規約とレビュワー共通指示

### 4.1 開発途中の手戻り・再検証・再レビュー規約
開発ライフサイクルの各ステージ進行中において、サブエージェントレビュー（Gate 1〜3）での指摘、またはユーザーからの仕様変更・改善指摘によって手戻り（Rework）が発生した場合、以下のプロトコルを厳格に適用する：

1. **安易な対症療法（インプレースパッチ）の禁止**:
	- レビュー指摘やユーザー指摘に対し、実装コード（Stage 6）のみを直接書き換えて済ませる行為を固く禁止する。
2. **手戻り起因ステージへの確実なバックトラック**:
	- **設計変更を伴う場合**: Stage 2（設計書改訂）へ戻り、設計書を更新した上で **Stage 3（設計レビュー・Gate 1）を再受診**する。
	- **テスト観点の不足・漏れの場合**: Stage 4（テスト設計）へ戻り、テストケースを追加・拡充した上で **Stage 5（テスト網羅性レビュー・Gate 2）を再受診**する。
	- **実装不具合・カバレッジ未達の場合**: Stage 6（実装・クリーンアップ）で修正後、**Stage 7（機械的構文チェック・変異の当て直し）およびStage 8（全テスト実行・カバレッジ検証）を再実行**する。
3. **先行検証手続きの連鎖的再実行（Cascading Re-verification）**:
	- 上流ステージ（Stage 2やStage 4）へ戻った場合は、そこから後続するすべてのステージ（機械的構文チェック・変異の当て直し・テスト実行・カバレッジ検証・Gate 3最終監査）を一連のシーケンスとして再度通過しなければならない。途中のゲートを「前回到達したから」という理由で省略してはならない。
4. **文書だけの指摘の扱い（ゲートを止めずに並行して直す）**:
	- ゲートの指摘が、設計書・追跡表・レビュー記録の表現や記述の精度だけに関するもの（以下、文書だけの指摘）である場合は、そのゲートを通過とし、後続のステージへ進む。指摘は並行して文書へ反映する。
	- 次のいずれかに関わる指摘は、文書だけの指摘としない。1件でもあれば、従来どおり 2. に従って該当するステージへ戻る。
		- 挙動・仕様の欠落や矛盾により、実装がどう動くべきか決まらないもの
		- 退行
		- 欠陥を検出できない試験
		- セキュリティ（4.5）
	- 指摘に両方が含まれる場合は、文書だけの指摘を並行して直しつつ、残りの指摘について該当するゲートを再受診する。
	- 並行して直した文書は、次のゲート（最後は Gate 3）の審査対象に含め、依頼文で変更点を示す。
	- Gate 3 の文書だけの指摘を直した文書には、後続のゲートがない。これらは Stage 12 の PR レビューで確かめる。PR 本文のレビュー結果（5.）に、Gate 3 の後に直した文書と内容を列挙する。
	- ゲートの記録には、文書だけの指摘であったこと、反映した内容、通過とした理由を残す。
	- 仕様の規則は、長い1段落に書かず、用語の定義と箇条書きの規則に分けて書く。一つの規則に例外を重ねて書くと読み違いが生じ、文言だけの差戻しが続くためである。
5. **将来のコードの潜在の経路だけの指摘の扱い（反映して通過）**:
	- ゲートの指摘が、現行のコードで実証できる欠陥・退行・試験の検出力の欠落ではなく、将来のコードが検査（字句の固定の静的試験など）をすり抜けうる潜在の経路だけである場合は、その経路を検査（禁止の名前・許可リストなど）に加えて設計・試験へ反映し、そのゲートを再審査なしで通過とする。
	- 指摘に現行のコードの欠陥・退行・試験の検出力の欠落が1件でも含まれる場合は、従来どおり 2. に従って該当するステージへ戻る。
	- 反映した内容は、次のゲート（最後は Gate 3）の審査対象に含め、依頼文で変更点を示す。
	- Gate 3 の指摘を反映した場合は後続のゲートがないため、試験・コードを変えたときは Stage 7・8（構文・空白の検査、変異の当て直し（変えた行への `--auto --since` と一覧の変異。単位ごと）、全件試験・カバレッジ）を再実行してからコミットする。反映した内容は PR 本文のレビュー結果に列挙し、Stage 12 の PR レビューで確かめる。
	- ゲートの記録には、潜在の経路だけの指摘であったこと、反映した内容、通過とした理由を残す。
	- 字句の固定のような網羅しきれない検査では、同じ種類の潜在の指摘が回を重ねても尽きにくく、再審査を繰り返すと手戻りが長引くためである（R-25 の Gate 1 で11回を要した）。
6. **変更外の指摘の扱い（記録して通過）**:
	- 比較元は、今回の作業の着手前のコミットとする（Stage 1 で決めて記録に書き、スクリプトの `--base` と同じものを使う）。
	- 変更外の指摘とは、比較元でも同じく成り立ち、今回の変更がそれを生じさせも悪化させもしていない指摘をいう。今回の変更で変えていない箇所に現れても、今回の変更が原因であるもの（退行）は変更外としない。
	- 判定の手順: 同じ再現手順（操作・入力・観測する出力）を、比較元の作業コピーと作業ツリーの両方で実行し、観測結果が一致した場合だけ変更外とする。結果が異なるとき、比較元で再現しないとき、再現手順を定められないときは、通常の指摘とする。両方の結果をゲートの記録と残件台帳に残す。
	- 再現の経路が Stage 2 の影響範囲の一覧の関数・データを通るときは、結果の一致を必ず確かめる。今回の変更で値が変わる経路の上にある、変えていない箇所の問題は、退行でありうるためである。
	- 新しい経路の確認: 今回の変更が、問題の箇所へ新しい経路を作っていないかを確かめる。問題の箇所の関数の呼出元を `finding-scope.js`（`impact.js --callers` を使う。「呼出元の変更」の列。差分の中・外の js の参照とも）でたどり、データは `impact.js` で読み書きする箇所を一覧にする。比較元から増えた・変わった呼出元や読み書きの箇所があれば、その経路でも比較元と作業ツリーで再現する。比較元で成り立たない経路が1つでもあれば、通常の指摘とする。
	- `finding-scope.js` による「行が差分の中か外か」は補助の情報であり、それだけで変更外としない。
	- 変更外の指摘は、そのゲートを通過とする。内容は残件台帳に記録し、ゲートの記録と PR 本文から参照する。ただし配信側（サーバー・ホスティング・HTTP 応答ヘッダー・TLS・公開の範囲）の事項は、4.7 のとおり台帳に載せず、設計書に範囲外・前提として書く。
	- 判定の確認: 実装者が今回の作業の中で変更外とした項目（接頭辞のない指摘を変更外とした場合を含む）は、独立のレビュワーが確かめる。次の回の依頼文に、再現手順と比較元・作業ツリーの両方の結果を付けて示す。そのゲートを通過した場合は次のゲートの依頼文に、Gate 3 の後に変更外とした場合は PR 本文（Stage 11 の 5.）に示す。レビュワーが判定を誤りとした項目は、通常の指摘とする。
	- 例外:
		- セキュリティの問題（4.5）は、利用者に報告し、今回直すか台帳に送るかの決定を得るまで、そのゲートを通過としない。配信側の事項は、台帳に送る代わりに設計書に範囲外・前提として書くことの決定を得る。
		- 受入れの判定を不安定にするもの（失敗する・不安定な試験、基準を割るカバレッジ）は、台帳に記録したうえで、別のコミットで直してから通過とする。
	- 今回の変更の中で直すと決めた変更外の指摘は、通常の指摘と同じく扱う。
7. **2回目以降の審査の範囲**:
	- 各ゲートの1回目は全範囲を審査する。2回目以降は、前の回の指摘の是正と、その是正が持ち込んだ問題を重点として審査する。依頼文には、前の回の指摘と是正の差分と、残件台帳の未対応・見送りの項目を示す（今回の作業で記録した項目には、再現手順と両方の結果を付ける。6.）。
	- 重点の外で見つけた指摘も、分類は1回目と同じとする。先に変更外かを判定し（6.）、次に文書だけ（4.）・将来の潜在の経路だけ（5.）・ゲートを止める指摘（4.4）に分ける。重点の外であることだけを理由に、台帳へ送ったり通過としたりしない。
	- 要是正の回の数え方: ゲートを止める指摘（4.4 の接頭辞なし）が1件以上あった回を要是正の回とする。同じゲートで要是正の回が3回続いたら、実装者が指摘の傾向（同じ種類が続いているか、何が根本の原因か）をまとめて利用者に報告し、続けるか・停止の基準を設けるかを決めてもらう。通過した回と、利用者が続けると決めた回で数え直す。
8. **指摘はまとめて直す**: 1回の審査の指摘は、すべてを直してから次の回へ進む。直すたびに個別に検証・再審査を回さない。

### 4.2 完了後・本番稼働後ユーザー指摘における「横展開・テスト先行強化」プロセス
全ステージが完了（または本番運用後）し、リリース後にユーザーから不具合指摘や修正要望が寄せられた場合、単なるバグ修正にとどまらず、品質を根本から底上げするために以下の手順を義務付ける：

1. **ステップ1: 根本原因分析（RCA）と類似不具合の網羅的横展開調査（Horizontal Scan）**:
	- 指摘された不具合のメカニズムを特定する。
	- 単一箇所の修正で終わらせず、全コードベース（全11モジュール、HTML、CSS、ストレージ処理等）において「同じパターンの不具合」「類似の考慮漏れ」「同種のエッジケース脆弱性」が存在しないか、水平展開調査を実施する。`impact.js --callers 3` で、不具合に関わる名前の出現と呼出元を一覧にする。
	- 残件台帳の項目に同じ不具合・類似のものがないかを確かめる。
2. **ステップ2: テスト先行（TDD）による再現テストおよび類似ケースの網羅的追加**:
	- 着手前に、関わる試験を `repeat-tests.js` で（`run-units.js` で単位ごとに）繰り返し実行し、不安定な試験を別のコミットで直す（Stage 4 と同じ）。
	- プロダクションコードに手を加える前に、まずテストスイート（`tests/`）を改修する。
	- 指摘された不具合を確実に再現し、失敗（Red）することを確認するテストケースを実装する。
	- ステップ1の横展開調査で発見・懸念された類似パターン・境界値に対しても、同様に検知可能なテストケース（正常系・境界値・異常系）を網羅的に追加する。
3. **ステップ3: テスト修正内容の確認およびテスト観点レビューの実施**:
	- 拡充されたテストスイートが、不具合およびその類似ケースを漏れなく捉えられているかを確認する。
	- 修正の下書きを作り、`mutate.js` で（`run-units.js` で単位ごとに）変異を当てて生存がないことを確かめる。比較元から変えた本番のファイルの下書きの写しを、作業ツリーの外に保存する（ステップ4の当て直しの `--since` に使う。Stage 4 と同じ）。`precheck.js --base <比較元> --pending <この回の記録>` を実行する。
	- サブエージェントによるテスト充足性レビュー（Gate 2相当）を受診し、テスト設計の妥当性の承認を得る。
4. **ステップ4: プロダクションコードの修正・機械的構文チェック・変異の当て直し・デッドコード排除**:
	- テストを通過（Green）させる実装修正を行う。
	- `precheck.js --base <比較元>` による機械的構文・空白・文書チェックを通過させる。
	- ステップ3で当てた変異の一覧と、修正の下書きから変わった行への `mutate.js --auto --since <下書きの写し>` を、最終のコードに当て直す（Stage 7 と同じ）。
5. **ステップ5: 全テスト実行・カバレッジ検証および最終監査（Gate 3）**:
	- `verify-twice.js` を実行し、全テスト合格（0件失敗）、Line 100%、Branch 95%以上、実行の前後の SHA-256 の不変を再検証する。
	- サブエージェントによる最終包括品質・セキュリティ監査を受診し、正式な合格判定を得てコミット・リモートpush・PRへ移行する。コミットの前に `precheck.js --base <比較元> --verified <検証記録>` を実行する。

### 4.3 レビュワー（サブエージェント）共通指示規約
各ゲート（Gate 1〜Gate 3）を担当するすべての独立レビュワー（サブエージェント）は、以下の指示事項を厳格に遵守してレビューを実施しなければならない。

レビュワーのモデル・提供元は限定しない。Codexの独立サブエージェントも利用可能である。実装担当自身の自己レビューを独立レビューとみなしてはならない。過去レビューの担当者名は当時の記録であり、以後の担当指定ではない。

1. **Mermaid図示時の構文エラーチェック義務**:
	- レビュー報告書内に Mermaid 図（フローチャート、シーケンス図等）を含める場合は、構文エラーチェック（特殊記号のエスケープ、不正なノード接続、括弧の整合性）を必ず事前に実施し、レンダリングエラーのない完全な構文で記述すること。
2. **審査の範囲（4.1 の 7.）**: 2回目以降は、依頼文に示した前の回の指摘の是正と、それが持ち込んだ問題を重点として審査する。重点の外で見つけた問題も、4.4 の区分（変更外:・文書:・将来:・接頭辞なし）で同じく分類する。
3. **残件台帳の項目**: 依頼文に付けた残件台帳（`docs/review_backlog.md`）の項目は、次のとおり扱う。
	- 今回の作業の前に記録した未対応・見送りの項目は、既知として扱い、挙げ直さない。その項目が今回の変更で悪化している場合だけ、通常の指摘とする。
	- 今回の作業の中で記録した項目（実装者が変更外とした判定）は、依頼文の再現手順と両方の結果から、判定が正しいかを確かめる（4.1 の 6.）。正しくなければ、接頭辞なしまたは該当する区分の指摘として挙げる。
4. **不足観点（設計・実装・テスト）の徹底精査義務**:
	- 提出された成果物の正しさ（Positive Check）を確認するだけでなく、**「不足している設計はないか」「考慮が抜けている実装や潜在バグはないか」「検証されていないテスト観点や境界値はないか」**という批判的・網羅的観点（Negative/Gap Check）から徹底的に精査し、不足事項を指摘すること。

### 4.4 コードレビュー（Gate 1〜Gate 3）の基本原則および重点検査項目

#### 基本原則
* **レビューの目的は、欠陥・問題を検出することにある。**
* **お世辞、挨拶、要約、エグゼクティブサマリー、スコアカード（点数付け）、Mermaid図は一切出力しない。**
* **問題点が存在しない場合のみ、出力全体として「PASS」と1単語のみ返す。**
* **問題点が検出された場合は、以下のフォーマットのみで簡潔に箇条書きで出力する。**
  `<ファイル名>:<行番号>: <指摘内容（理由と修正すべきプロパティ名・引数）>`
* **文書の表現・記述の精度だけに関する指摘（4.1 の 4. の文書だけの指摘）は、指摘内容の文頭に「文書:」と付けて区別する。** 挙動・仕様の欠落や矛盾・退行・試験の検出力・セキュリティに関わる指摘には付けない。
* **将来のコードが検査をすり抜けうる潜在の経路だけの指摘（4.1 の 5.）は、指摘内容の文頭に「将来:」と付けて区別する。** 現行のコードで実証できる欠陥・退行・試験の検出力の欠落には付けない。
* **今回の変更で生じたものではない（比較元でも同じく成り立つ）と考える指摘（4.1 の 6.）は、指摘内容の文頭に「変更外:」と付けて区別する。** 退行には付けない。変更外とするかの最終の判定は、実装者が 4.1 の 6. の手順で行う。
* **頭に何も付けない指摘は、今回の変更による欠陥・挙動や仕様の欠落・矛盾（実装がどう動くべきか決まらないもの）・退行・試験の検出力の欠落・セキュリティの問題（ゲートを止める指摘）とする。** 4.1 の 4. で文書だけの指摘としないものと同じである。1件でもあれば、4.1 の 2. に従って該当するステージへ戻る。

#### 重点検査項目
1. **存在しないプロパティ名・メソッド名の参照**（呼び出し先の実装・スキーマと一致しているか）
2. **オブジェクト生成時における必須プロパティ（特に id, type, date, target_month 等）の欠落**
3. **ID体系の不一致や誤った同一視**（例: `tx.id` と `group_id` の混同、プレフィックスの不整合）
4. **ドメインルール（`type: 'expense' | 'income' | 'transfer'` 等）に存在しない値の使用**
5. **戻り値の型不一致**（配列を期待する箇所でオブジェクトを扱う、null/undefined の考慮漏れ）
6. **画面要素（DOM）の取得・更新におけるIDのタイポおよび多重イベントリスナー登録の有無**

### 4.5 セキュリティ専用アセスメントと是正ゲート

通常の機能レビューとは別に、セキュリティ専用のシステム・テスト・コードレビューをGate 1〜3で行う。カバレッジ達成のみを安全性の根拠としてはならない。

1. **脅威モデルと入力・出力台帳**: 保護対象、攻撃者の能力、信頼境界、平文保存を選択した場合の限界、file/HTTPS起動の差を記録する。フォーム、URL、ファイル、JSON、復号済み内容、LocalStorage、他タブ、Service Workerメッセージを入力として列挙し、HTML本文・属性・イベント・CSS・URL・印刷・保存・外部送信へ至る経路を追跡する。
2. **XSSとブラウザ防御**: HTML・属性・JavaScript・CSS・URLの文脈を区別する。HTMLエスケープをコード文脈へ流用しない。ユーザー値をイベントコードへ埋め込まず、任意式評価・`eval`・`Function`・文字列タイマー・動的グローバル関数解決を禁止する。イベントは外部スクリプトの固定処理へ登録し、CSPでインラインスクリプト・イベントを拒否する。CSPは入力検証・安全な描画の代替ではない。
3. **受入検証と可用性**: 認証済み暗号文・保存復元も不信入力である。スキーマ、真偽値、予約プロパティ、オブジェクト所有キー、座席寸法、ファイル/JSON容量・深さ・件数・日付範囲を状態変更前に検証する。任意項目も存在時の型を明示し、特にパスワード等の機微項目を文字列変換へ暗黙委譲しない。検証・正規化・描画がすべて成功するまで本状態を確定せず、描画例外時も旧状態・DOM・保存値を保持する。辞書は継承プロパティを参照・変更しない。
4. **暗号化・認証・並行処理**: 暗号文改竄・別保存先への差替え、認証メタデータ破損・削除、ロック中書込み、処理完了順序、他タブの全消去・鍵再設定、休止からの復帰を検査する。複数キー更新と同じ共有保存領域の通常読込・平文保存・暗号化保存・全消去を共通の排他境界で扱い、ロック取得後に保護状態を再評価する。保存要求時のデータとセッション世代を保持し、全消去・再設定・ロックをまたいだ待機要求を拒否する。照合直後、各キー書込間、失敗時復元中、および全消去の前後へ別タブ操作・同一タブ自動保存を割り込ませ、部分保存、旧値の復活、平文への降格、新しい値の上書きがないことを実コンテキスト間テストで確認する。保護状態不明時は平文へ移行しない。鍵の生バッファは成功・例外とも可能な範囲でゼロ化し、JavaScriptのコピー・GCまで消去保証できると表現しない。
5. **通信・PWA・運用境界**: 外部送信は明示操作に限定する。新規ウィンドウのopener、フォーム送信・base変更、同一originの別アプリのキャッシュ/SWへの干渉、任意URLの永続キャッシュを確認する。Service Workerでは、filtered responseから非公開となるヘッダーをJavaScript検査だけで保証したとみなさず、匿名要求・固定許可リスト・配信契約を併用する。公開時のTLS・HTTPヘッダー・実認証器は、未検証ならその旨を明記し、ローカル検査のみで合格としない。
6. **攻撃を先に再現するテスト**: 各指摘に識別子・重大度・成立条件・影響・再現手順・根拠テストを付す。悪意ある文字列を取込→保存→実再起動→通常画面→印刷へ通す。実行フラグ、攻撃DOMの不生成、既存DOM/保存値の保全、遅延イベント、拒否時の通知を確認する。暗号化やスキーマのスタブで攻撃経路を隠さない。
7. **独立した合否判定**: Gate 1は脅威と防御設計、Gate 2は攻撃経路と拒否の検査能力、Gate 3は全セキュリティ指摘の解消と回帰・残余リスクを判定する。実証済み問題と潜在的な多層防御不足を区別する。必要な是正を未実施のままPASSにしてはならない。ただし、比較元からある（変更外の）セキュリティの問題は、利用者が台帳に送る（配信側の事項は設計書に範囲外・前提として書く）と決めた場合に限り、未是正のまま通過とできる（4.1 の 6.）。適用外・実機未検証は理由を記録する。
8. **外部工程が拒否された場合**: 自動承認・認証・権限でpushやPRが阻まれた場合は迂回せず、送信先・送信内容・必要な承認/認証と未完了工程を明記する。ローカルで可能な是正・検証・レビュー・コミット・PR本文準備は先に完了する。

- 試験（`tests/unit/dev-scripts-<スクリプト>.test.js`。共通の補助は `tests/helpers/dev-scripts.js`）で、各スクリプトの判定の関数を確かめる。スクリプトごとにファイルを分け、変異の当て込みや繰り返しの実行を、スクリプトと試験の組ごとに行えるようにする。
- スクリプトの判定は機械的な補助であり、ゲートの審査の代わりではない。

### 4.7 残件台帳（docs/review_backlog.md）

- 記録するもの: 変更外の指摘（4.1 の 6.）、利用者の決定で反映を見送った指摘、作業を要する未検証の境界・残余リスク。
- 記録しないもの: 配信側（サーバー・ホスティング・HTTP 応答ヘッダー・TLS・公開の範囲）の設定に依存し、このリポジトリから制御できない事項。これらは設計書の範囲外・前提として書く（台帳に載せると、対応できないまま残り続けるため）。
- 各項目に、識別子（`BL-<連番>`）・記録日・出典（ゲートと回、記録へのリンク）・対象（ファイル・行または仕様の節）・内容・区分・状態を書く。
	- 区分: 変更外（再現手順と、比較元・作業ツリーの両方の結果を内容に書く）／見送り（利用者の決定）／残余（未検証の境界・残余リスク）
	- 状態: 未対応（備考）／対応済み（コミット・記録）／見送り（理由）
- 運用:
	- ゲートの依頼文に、未対応・見送りの項目を付ける（4.3 の 3.）。今回の作業で記録した項目には、再現手順と両方の結果を付けて、判定の確認を求める（4.1 の 6.）。
	- Stage 1 で、今回の変更の範囲に関わる未対応の項目を確かめ、対応するか見送るかを決めて状態を更新する。
	- PR 本文のレビュー結果に、追加・更新した項目の識別子を列挙する（Stage 11）。
	- 対応したときは状態を更新し、対応したコミット・記録を書く。項目は消さない。

## 5. 規約と品質基準

| 項目 | 基準 |
| :--- | :--- |
| **ブランチ戦略** | `main` 直接コミット原則禁止、`feature/*`, `fix/*`, `docs/*` によるPRベース運用（※明示的指示時を除く） |
| **PRフォーマット** | `.github/pull_request_template.md` 準拠（日本語5大項目の記載必須） |
| **テスト観点網羅** | **正常系・境界値・異常系のすべてを漏れなくテスト実装** |
| **UIテスト** | **ヘッドレスChrome（Chromium）による実ブラウザUIテストの自動実行（`npm run test:ui`）** |
| **機械的構文チェック** | 実装後直ちに `node tests/scripts/precheck.js --base <比較元>`（全 js の `node --check`・グローバルの重複・`git diff --check`・新規ファイルの空白と末尾の空行・文書の機械的チェック）を実行（違反0件）。Gate 3 の前に最終のコードへ変異を当て直す（`mutate.js`） |
| **監査前の機械的チェック** | `tests/scripts/` のスクリプト（4.6）を表の時点で実行し、判定するスクリプトは終了コード 0 を確かめる。コミットの前に `precheck.js --base <比較元> --verified <検証記録>` を必ず実行する |
| **静的型・参照の整合性**| 存在しないプロパティ/メソッド参照、DOM IDタイポ、戻り値型、ドメイン値。機械的に網羅できないため、試験（単体・実Chromium）と Gate 3 の重点検査項目で確かめる（原則4の例外） |
| **空白・インデント検証**| `git diff --check` を実行（タブインデント規約違反、末尾空白、空行違反0件） |
| **コードレビュー基準** | **基本原則遵守：問題なし時は「PASS」の1単語のみ返却。問題あり時は `<file>:<line>: <指摘>` のみ出力** |
| **重点検査項目** | ①未存在プロパティ/メソッド ②必須プロパティ欠落 ③ID体系不一致 ④ドメイン値逸脱 ⑤戻り値型/null不備 ⑥DOM IDタイポ/多重リスナー |
| **完了定義 (DoD)** | ローカルコミットにとどまらず、リモートリポジトリへの `git push` までを必須完了要件とする |
| **手戻りプロトコル** | 指摘発生時は起因ステージへ遡及し、後続の全先行検証・レビューを連鎖的に再実行（文書だけの指摘はゲートを通過とし並行して反映。将来のコードの潜在の経路だけの指摘は検査に加えて通過。変更外の指摘は比較元と作業ツリーで同じ再現の結果と新しい経路がないことを確かめたうえで残件台帳に記録して通過し、次の回に独立のレビュワーが判定を確かめる（セキュリティは利用者の決定、受入れを不安定にするものは別のコミットで直す）。2回目以降は前の回の是正を重点に審査し、要是正が3回続けば利用者に報告。Gate 3 の後に直した文書は PR レビューで確認） |
| **残件台帳** | 変更外・見送りの指摘と作業を要する残余を `docs/review_backlog.md` に記録し、状態を更新する（項目は消さない）。配信側の事項は載せず、設計書に範囲外・前提として書く |
| **完了後不具合対応** | 類似不具合の全コードベース横展開調査、およびテスト先行強化（TDD/Red-Green）・テストレビュー必須 |
| **外部依存性** | 外部 npm ランタイムライブラリゼロ（Node.js / Web標準技術のみ） |
| **テスト合格率** | 100%（全件パス、失敗0件） |
| **コードカバレッジ** | Line 100.00%（全モジュール）、Branch 95.00%以上（全モジュール） |
| **インデント規約** | 全ファイル（JS, HTML, CSS, MD, JSON）タブインデント（`\t`） |
| **セキュリティ基準** | AES-256-GCM、PBKDF2-HMAC-SHA256 600,000回（旧100,000回は読込移行のみ）、WebAuthn PRF、CSP強制、XSSエスケープ |
