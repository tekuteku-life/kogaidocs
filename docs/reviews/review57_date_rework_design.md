# 日付・自動祝日補完の手戻り設計レビュー（Gate 1）

**実施日**: 2026年10月24日<br>
**対象**: 外部仕様E-09-02、内部仕様I-03、`review55_import_security_assessment.md` のSEC-19改訂と先行テスト計画

## 手戻り理由

先行テストにより、有効な9998年でも現行の春秋分近似式が実在しない日付を返し、生成された休日の再検証で取込が失敗することが判明した。翌年を9999へ抑えるだけの初期設計では、受入可能な有効ISO日付について描画前検証と原子性を維持できない。低年ではDate.UTCの年0〜99の特殊扱いも考慮が必要である。

本記録は、`review56_specifications_design.md` のSEC-19における自動祝日生成の年範囲についての判定を、次の改訂設計で更新する。SEC-18と仕様分割に対する先行レビューは維持する。

## 改訂設計の確認

- 空でない開始日・終了日は片側だけでもISO実在日を要求する。両側がある場合に順序・3,660日上限を検査し、空の片側は下書きとして許す。
- 休日省略時の自動補完は開始年2000〜2099だけを対象とし、翌年の終端も2099までに制限する。
- 対象年の範囲外でも有効なISO期間を拒否せず、休日を空へ補完する。低年・遠未来の近似計算を描画経路へ持ち込まない。
- 利用者が明示した有効な休日と空文字は、自動補完範囲の制限で上書きしない。
- この年範囲は技術上の自動補完の実行範囲であり、法改正・特例を含む祝日暦の正確性保証と区別する。

外部仕様、内部仕様、セキュリティ評価の改訂が同じ契約であることを確認した。無効な春秋分だけを黙って除外して部分的な暦を返す方式より、補完範囲を明示する方式が説明可能である。日付の受入可能範囲と暦の自動補完範囲も区別できている。

## 先行テスト計画の確認

`tests/unit/security-import-lifecycle.test.js` の追加ケースを読み、0・1・99・100・1999・2000・2099・2100・9998・9999年を実暗号化地区取込へ通す計画を確認した。成功通知、地区モデル、日付DOM、補完休日の型と内容、2100年への越境防止、範囲外の空補完を直接検査している。明示された空文字と9999年の有効休日を保持するケースも存在する。

不正な単独start/end、非実在日、空の下書きは既存の先行計画を維持し、公式JSON・ファイル・貼付・平文保存・暗号化保存の受入境界で状態・DOM・保存原本の保持を検査する。実Chromiumでは不正な単独端点、公式JSON、9999年、年度更新時の旧別名を補完する計画である。

## 判定

改訂設計と先行テスト計画に対するGate 1は合格である。本線は未修正であり、本記録は実装・テスト結果の合格を意味しない。追加テストのRed原因を分類し、Gate 2、本線修正、全回帰、最終Gate 3を順に実施する必要がある。
