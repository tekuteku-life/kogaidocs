## 1. エグゼクティブサマリー

本報告書は、`kogaidocs 開発プロセス定義書 (v1.0.0)` の **Stage 3: 設計レビュー＆セキュリティアセスメント（第1ゲート）** に基づき、独立したシニアシステムアーキテクトおよび主任セキュリティ評価者の観点から、改訂された `docs/system_design.md (v2.2.0)` および `docs/development_process.md (v1.0.0)` を対象に実施した包括的な技術・セキュリティ監査の結果を取りまとめたものである。

### 1.1 評価の結論
改訂されたシステム設計書（v2.2.0）は、ユーザーから提示された6項目の機能拡張・UX改善要求に対し、単なる局所的パッチにとどまらず、システム全体の中核思想である **「サーバーレス・ゼロトラスト・ローカルファースト」** に即した**全体最適（あるべき姿）** として整合的に昇華されている。

特に、Web Cryptography API（AES-256-GCM）および WebAuthn PRF 拡張を中核とする端末内暗号化ストレージ機構を堅持しつつ、現場の利便性を損なわない「ファイルパスワードの安全記憶機構（オプトイン＆暗号化ストレージ連動＆揮発性保証）」や「リアルタイム全角サニタイズ（IME制御＆キャレット位置保護）」の設計は、高いセキュリティと優れたユーザビリティを極めて高度に両立させている。

一部、外部共有機能（LINE / mailto）におけるURL長制限による暗号文切断リスクや、状態管理層での防御的二重防壁の実装要件など、次期ステージ（Stage 4: テスト設計 / Stage 6: 本線実装）で確実に反映すべき是正措置（アクションアイテム A-1 〜 A-5）を検出したため、判定は **「条件付き合格（CONDITIONAL PASS）」** とする。本提言事項をテストスイートおよび実装に組み込むことで、極めて堅牢な本線リリースが可能と判断する。

## 2. 開発プロセス定義書（docs/development_process.md）の妥当性評価

策定された `docs/development_process.md (v1.0.0)` について、ソフトウェア工学プロセスおよび品質保証ライフサイクルの観点から精査した。

### 2.1 ライフサイクル設計の妥当性
- **Stage 1 〜 Stage 9 の直列ゲート構造**:
	- 要求分析から設計改訂、設計レビュー、テスト設計、テストレビュー、実装、カバレッジ検証、最終QA、コミットに至る9ステージ制を採用しており、手戻りを防止するウォーターフォール型の厳格性と、TDD（テスト駆動開発）の俊敏性を兼ね備えた優れた構成である。
- **3段階の独立サブエージェント・クオリティゲート（Stage 3, 5, 8）**:
	- 実装担当者とは独立したレビュアーが「設計書（review2_design.md）」「テストケース網羅性（review3_tests.md）」「最終実装・テスト結果（review4_final.md）」の3つの関門で合否判定を行う体制は、児童個人情報等の最重要機微データを扱うシステムにおいて極めて適切かつ必須のプロセスである。
- **完全ゼロ外部依存性（Zero External Dependencies）原則**:
	- Node.js 組み込みテストランナー（`node:test`）、アサーション（`node:assert`）、Web Cryptography API のみを活用し、npm 外部パッケージ依存ゼロを義務付けている点は、サプライチェーン攻撃（悪意あるサードパーティパッケージ混入）リスクを原理的に根絶するものであり、高く評価できる。
- **高水準カバレッジ基準（Line 100.00% / Branch 95.00%以上）**:
	- 機微データをクライアント側で完全処理するシステムとして、デッドコードを許容せず、全分岐を検証する基準は妥当である。

### 4.2 パスワード記憶機構の安全性評価
1. **LocalStorage平文保存の完全排除**:
	- `currentDistrict.savedFilePassword` は、`state.js` 内のステートオブジェクトに一時的に保持される。
	- これをLocalStorageに永続化する際、必ず `saveStorageData()` が介在し、暗号化が有効な場合は `STORAGE_ENC:{base64}` の形式でAES-256-GCM暗号化された上で格納される。
	- したがって、ブラウザの開発者ツールやディスクダンプから平文パスワードが漏洩することは構造的にあり得ない。
2. **暗号化ストレージへの抱き合わせ保存の妥当性とリスク**:
	- 端末暗号化マスター鍵（WebAuthn PRF または マスターパスワードから導出）が「金庫の鍵」となり、その金庫の中に地区提出用ファイルパスワードが保管される二重エンベロープ暗号構造（Key Wrapping Architecture）を形成している。
	- 暗号学的に正当な階層型鍵管理（Hierarchical Key Management）モデルに合致している。
3. **揮発性・ライフサイクル管理の妥当性**:
	- アプリロック時に `clearMemoryAndDomForLock()` が実行され、インメモリの `currentDistrict` およびDOM要素（`#d-pass`, `#d-pass-confirm`, `#d-load-pass`）の値が空文字に初期化される。
	- ロック中は、生体認証（Touch ID / Windows Hello）またはマスターパスワードを再入力しない限り、ファイルパスワードへのアクセスは一切遮断される。
	- さらに「年度更新（新年度化）」時には、役員情報・児童名簿とともに `savedFilePassword` が完全に初期化（消去）されるため、次年度役員への意図しないパスワード引き継ぎ・残留リスクも排除されている。

### 4.3 外部共有機能（LINE / mailto / Web Share API）の安全性評価
1. **暗号文限定の伝送**:
	- 共有対象は暗号化出力されたファイル（`.txt`）または暗号化テキスト（`BEGIN_DATA:...:END_DATA`）のみであり、児童・役員の個人情報が生データとして送信される経路は存在しない。
2. **URL長制限と暗号文切断リスクの分析**:
	- **課題**: `mailto:?body=...` や `https://line.me/R/msg/text/?...` 等のURIスキームには、オペレーティングシステム（Windows、iOS、Android）やメーラー（Outlook、Apple Mail等）、ブラウザによって **2,048文字〜4,096文字程度のURL長制限** が存在する。
	- 児童数100名規模の地区データでは、暗号化Base64文字列が 15KB〜25KB を超える。
	- これを直接URLクエリパラメータに埋め込んだ場合、URLが途中で切り捨てられ、AES-GCM認証タグ（末尾16バイト）が欠落して復号時に必ずエラーとなる、あるいはメーラー自体が起動しない障害が発生する。
	- **対策方針**: 設計書において、Web Share API（ファイル添付）およびクリップボードコピーを第一選択とし、直接URL埋め込みを行う場合はサイズ上限チェック（2,000文字以内）または「案内文のみ送信し、暗号化テキストは別途貼り付けさせる」フォールバックの仕様化が不可欠である（改善提言 A-1）。

### 4.4 パスワードサニタイズ処理の堅牢性評価
1. **XSSおよびDOM操作副作用の評価**:
	- `sanitizePasswordInput(el)` は、DOM要素の `value` プロパティに対して直接文字列操作を行い、HTMLマークアップを生成しないため、DOM-based XSSの混入リスクはゼロである。
2. **バイパス可能性の評価**:
	- 仮想キーボードによる入力（`input` イベント）、物理キーボード入力、クリップボードからの貼り付け（`paste` イベント後の `input`）、ブラウザの自動補完のすべてが `input` イベントを経由してサニタイズ処理を通過するため、バイパスの余地はない。
3. **キャレット制御の留意点**:
	- 全角ASCII（`U+FF01`〜`U+FF5E`）を半角ASCIIへ変換する際は1文字対1文字の置換であるため文字長は変化せず、キャレット位置は維持される。
	- しかし、非ASCII文字（ひらがな・漢字）や全角スペースを除去した場合、文字列長が短縮される。カーソル以前に存在した削除文字数分だけキャレット位置を左にシフトさせなければ、文字入力中にカーソルが予期せず右へ飛ぶUX不整合が生じるため、正確なオフセット計算が必要である（改善提言 A-3）。

### 4.5 日本国個人情報保護法（APPI）適合性評価
- **法第22条（消去の義務）への準拠**:
	- PTA役員は1年任期が原則であり、利用目的を終えた個人情報の速やかな消去が義務付けられる。本システムの「年度更新（新年度化）」機能は、児童の進級処理・卒業児童削除とともに、任期満了した役員の氏名・連絡先および記憶されたファイルパスワードを端末内から完全に消去する仕様となっており、法第22条の要請を完全に充足している。
- **法第23条（安全管理措置）への準拠**:
	- 技術的安全管理措置として、保存時および移送時の暗号化（AES-256-GCM）、総当たり攻撃耐性（PBKDF2 100,000回）、端末認証バインド（WebAuthn PRF）、離席時の自動ロック（15分タイマー / タブ非表示検知）が一貫して施されており、個人情報保護委員会のガイドラインが要求する「高度な暗号化による安全管理措置」を十分にクリアしている。
- **法第27条（第三者提供の制限）への準拠**:
	- 外部クラウドや中央サーバーを一切介さない完全ローカル完結型アーキテクチャであり、開発者や第三者事業者への個人情報提供・預託が原理的に発生しない。

## 6. 設計改善提言・セキュリティ是正措置（アクションアイテム A-1 〜 A-5）

次期ステージ（Stage 4: テスト設計 / Stage 6: 本線実装）に向けて、以下の5つの是正措置を反映することを勧告する。

### [A-1] 外部共有におけるURL長制限・暗号文切断リスクの設計明記と安全フォールバック（重要度：高）
- **内容**:
	- LINE共有（`https://line.me/R/msg/text/?...`）およびメーラー連携（`mailto:?body=...`）において、暗号化Base64テキストの全体サイズが 2,000文字 を超える場合、OSやクライアント側のURL長制限により暗号文が途中で切り捨てられ、復号不能となる恐れがある。
- **是正措置**:
	1. **Web Share API（ファイル共有）の最優先利用**: スマートフォン環境では `navigator.share({ files: [file] })` により暗号化 `.txt` ファイルそのものを共有させる。
	2. **大容量データ時の安全フォールバック**: 暗号文のエンコード長が 2,000文字 を超える場合、LINE / mailto のURLクエリに暗号文を直接埋め込むことを抑止し、クリップボードに暗号化テキストを自動コピーした上で、「校外委員会地区データを送信します。クリップボードにコピーされた暗号化テキストをここに貼り付けてください」という定型メッセージのみをパラメータとして開く設計とすること。

### [A-2] 状態管理（State）層におけるパスワード平文保存防止の厳格な二重防壁（重要度：高）
- **内容**:
	- 設計書4.6節において「端末内暗号化が有効な場合のみ記憶を許可する」と規定されているが、万が一UIのチェックボックス状態と暗号化初期化フラグの同期に不整合が生じた場合、LocalStorageに平文のまま `savedFilePassword` が書き込まれるリスクを完全に排除する必要がある。
- **是正措置**:
	- `state.js` の `saveDistrictLocal()` 内部において、以下のような状態層レベルのハードガードを必須仕様として明記・実装すること：
		```javascript
		// 端末暗号化が無効な場合は、UIチェック状態に関わらず保存対象からパスワードを強制除外
		if (!isStorageEncrypted()) {
			delete districtToSave.savedFilePassword;
		}
		```

### [A-3] パスワードサニタイズ時のキャレット位置補正アルゴリズムの明確化（重要度：中）
- **内容**:
	- `sanitizePasswordInput(el)` において、全角空白や非ASCII文字（かな・漢字）を削除（除去）した際、削除された文字数分だけカーソル位置を調整しなければ、キャレットが末尾に飛んだり予期せぬ位置にずれたりしてユーザー体験を損なう。
- **是正措置**:
	- キャレット位置補正ロジックを設計仕様として明確化すること：
		```javascript
		const origStart = el.selectionStart;
		// カーソル位置より前に存在する削除文字数を計算し、新しい selectionStart / selectionEnd を決定
		```

### [A-4] ERD（データモデル）への `savedFilePassword` 属性の反映（重要度：低）
- **内容**:
